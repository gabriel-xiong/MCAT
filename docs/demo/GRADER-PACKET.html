1. Executive summary

MCAT Speedrun is an Anki fork plus AnkiDroid companion that measures the gap between flashcard recall and exam-style performance. Students review in memory mode (standard FSRS scheduling) and practice curated OpenStax MCQs in a separate performance mode. The dashboard shows three scores that are never blended: Memory (FSRS recall strength), Performance (attempt accuracy on gated topics), and Readiness (section-mapped 472–528 range with explicit uncertainty). v1 is a measurement prototype, not a full prep course: shipped content covers 18 coarse topics (~200–500 cards, 170 performance questions) while the coverage denominator uses the full exam outline of 49 topics (data/mcat-outline.full.json). Prototype content presence yields roughly 6–37% outline coverage, so Readiness correctly abstains below the 50% gate rather than projecting readiness from a tiny slice of the MCAT. Every computed score carries a range or credible band, coverage context, a missing-data note when withheld, and a single next action—honesty over flattery is an automatic fail criterion for this submission.

2. Score models

Implementation: anki-MCAT/pylib/anki/mcat_scores.py (hand-mirrored in AnkiDroid). Full prose: docs/MODELS.md. Policy: docs/DECISIONS.md §7 (three scores), §8 (readiness direction), §14 (give-up thresholds), §31 (tester vs strict profiles).

2.1 Memory — FSRS recall strength

Question: How strong is flashcard recall right now, using memory-domain signals only (never outline coverage)?

Signals: Mean FSRS predicted retrievability R over all started cards with memory state; deck maturity Mat = fraction of started cards with scheduling interval ≥ 21 days.

Strict (graded) headline: MemoryScore = round(R × Mat × 100)
Tester (engagement) headline: MemoryScore = round(R × 100) — maturity factor forced to 1.0

Uncertainty band: Wilson interval on mean recall probability, scaled by the maturity factor (replaces normal SE, which collapses to ±0 at R≈1 right after review). Band widens at small card counts.

Memory abstain gates — two pre-registered profiles (SCORE_PROFILE)
GateStrict (graded claims)Tester (friend engagement only)
Graded reviews≥ 200 total revlog rows≥ 10
Card maturity≥ 1 card at interval ≥ 21 daysNot required
Started-card floor(governed by maturity)≥ 10 started cards
Score basisR × Mat (long-term recall strength)R only (“early recall strength”)
UI label when computedMeasured (if gates pass)Provisional badge — not a graded claim

The graded MSI build sets SCORE_PROFILE = "strict". Tester thresholds exist solely so a ~15–20 minute session can populate provisional tiles; they do not change graded eval claims (DECISIONS §31). Empty profiles (0 data) always abstain on all three scores.

2.2 Performance — Bayesian shrinkage accuracy

Question: On first-attempt exam-style questions in unlocked topics, what accuracy should we expect? Deliberately not memory × constant and not coverage-derived.

k = correct attempts, n = scored attempts (IDK excluded)
Prior: Beta(2, 2) — mean 0.5, effective prior n = 4
PerfScore = round(100 × (k + 2) / (n + 4))
Credible band: normal approximation to the same Beta posterior (±1.96·sd), displayed 0–100

Section accuracy is computed per topic via PerfStore.accuracy(); the headline uses pooled first-attempt correctness. Topic gate (performance unlock): ≥ 3 distinct cards seen AND ≥ 5 Good/Easy on that topic; CARS is always unlocked (no memory gate). IDK (“Not sure”): excluded from accuracy numerator and denominator; logged separately; non-CARS IDK routes to content_gap remediation without a scored attempt (DECISIONS §30).

Question bank split: 170 items — 65 dev (tuning) / 105 held_out (frozen before tuning; friend eval target). Runtime reads local bank only — no live LLM during scoring.

2.3 Readiness — mapped range with coverage penalty

Question: If the exam were today, what total score range is plausible?

  1. For each section (CP, CARS, BB, PS), compute mean scored attempt accuracy (IDK excluded).
  2. Map accuracy → section score: 118 + accuracy × (132 − 118) (118–132 per section).
  3. Sum section scores → center on 472–528 scale; apply half-width band.
  4. Abstain if any give-up gate fails (table below).
half_width = 6 + round(18 × max(0, (30 − n) / 30)) /* n = perf attempts */
range = [clamp(center − half_width, 472), clamp(center + half_width, 528)]
confidence = round(100 × (0.4·cov + 0.4·(n/(n+60)) + 0.2·(1 − min(width,30)/30)))
bucket: <40 low · 40–69 moderate · ≥70 high

Confidence uses readiness-domain inputs only (coverage fraction, attempt count, range width)—never Memory or Performance headline scores.

Readiness abstain / give-up gates (all must pass to show a range)
ConditionStrict thresholdTester threshold
Memory reviews≥ 200≥ 10
Performance attempts (scored)≥ 30≥ 8
Exam outline coverage≥ 50% of 49 topics≥ 50% (unchanged)
CP / BB / PS attempts each≥ 5 per shipped section≥ 3 per shipped section
CARS attempts≥ 5≥ 3

Coverage semantics (DECISIONS §2): Denominator = full 49-topic AAMC outline. Numerator = topics where the deck has tagged cards or the question bank has ≥1 question—content presence, not user study progress. With ~18 shipped topics represented in content, coverage stays well below 50%, so strict Readiness abstains by design until curriculum expands or the user is told honestly that the proxy cannot fire yet.

3. Locked design decisions

Bullet summary with decision-log references (docs/DECISIONS.md):

  1. Product shape (§1): Anki fork + measurement layer—not add-on-only or greenfield app. Shared Rust engine for desktop + AnkiDroid.
  2. Scope (§2, §3): ~15–25 prototype topics for shipped deck/UI; 49-topic full outline as coverage denominator only.
  3. Performance gate (§6, §8): ≥3 cards seen + ≥5 Good/Easy per topic; separate sessions from memory reviews.
  4. CARS (§9): Performance-only lane—no flashcard prerequisite.
  5. Three scores (§7): Memory, Performance, Readiness always separate with ranges; never blended into one “% ready.”
  6. Sidecar sync (§5, §22): Stock Anki sync for collection; performance data in local mcat_perf.db; cross-device perf via uuid-deduped export/import bundle (not embedded in collection DB).
  7. Question bank (§10, §13): Curated OpenStax with named sources; dev vs held_out frozen before tuning.
  8. AI at runtime for scores (§12, §23–§24): Wednesday deliverable = zero AI on critical path. Scores and question bank run fully offline. Optional post-answer explainer uses static explanation fields; live/proxy AI is a separate graded-build seam and falls back to static on block/error.
  9. Error typing — BrainLift (§9, §21): Ship 4 self-report types Wednesday; v2 infers 3-bucket taxonomy (content_gap, application, misread) with probe + confirm hypothesis UX; drives dashboard next action.
  10. Study feature (§11): Interleaved vs blocked vs plain Anki performance sessions at equal study time; 3-build ablation (Kornell & Bjork reference).
  11. IDK anti-guessing (§30): “Not sure” excluded from accuracy; passive readiness effect via no coverage credit on IDK-only topics.
  12. Profiles (§31): Strict gates for graded claims; tester gates for engagement only, with provisional labels and wide CIs.

5. What we measured vs. what we did not

Measured (with evidence)

  • FSRS calibration pipeline on synthetic revlog (Brier/log-loss/ECE) and on two real collections (builder n=39 test; alt participant n=38 test)—calibration only; strict Memory headline still abstains.
  • Held-out scoring pipeline (synthetic 3-tester pool)—proves pool_heldout.py / Wilson CI path works.
  • Paraphrase-gap instrument (synthetic demo)—recall vs reworded-question accuracy diverge (+0.16).
  • Step 2 prediction harness (synthetic features)—transparent logistic weights, not trained ML.
  • Leakage scan on 170-item bank; AI explainer eval vs static/TF-IDF baselines (offline + one live run).
  • Rust mastery query + undo integrity (4 + 15 automated checks); three-score separation in code and UI.

Not measured (stated honestly)

  • Independent held_out performance score — participant alt exported dev practice only (scorable: false).
  • Study feature causal claim — synthetic interleaved vs blocked inconclusive (p=0.057); no real equal-time 3-build data.
  • Real paraphrase gap — no paired recall JSON + held_out attempts from a volunteer yet.
  • Step 2 on live snapshots — no real held_out attempts with mastery at attempt time.
  • Two-device memory sync recording — rule documented; not captured on video.
  • MCAT outcome validation — readiness is an early proxy; AAMC full-lengths remain external gold standard.

7. Known limitations and post-submission backlog

  • No scorable held_out sheet — graded Performance remains ABSTAIN until a frozen answer template is returned and pooled.
  • Strict Readiness abstains on prototype coverage (~6–37% of 49-topic outline)—by design, not a bug.
  • 50k dashboard latency — historical bench ~2.9 s p50 at ~50k cards; mastery query alone stays fast (~19–300 ms).
  • Study feature — pipeline proven; headline hypothesis not supported at synthetic n (p=0.057).
  • MSI may be stale — graded installer rebuild may lag merged fork; verify commit in docs/GRADED-QUICKSTART.md / docs/PRE-DEMO-VERIFICATION.md before claiming “latest build.”
  • Mentor feedback (post-Sunday) — captured in docs/feedback/2026-07-05-demo.md (simplify miss UX toward binary prompts, real multi-arm study data, sync recording, live Step 2 snapshots). Not in submission scope unless reprioritized.
